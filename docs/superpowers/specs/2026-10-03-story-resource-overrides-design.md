# 剧情资源更新与玩家编辑保留设计

状态：用户已确认设计；实施计划待审阅，尚未实施存档格式变更。

## 目标与已确认规则

修复剧情持久化的两条冲突契约：资源升级刷新未编辑字段，玩家逐字段编辑优先保留。旧档没有可靠来源标记时，保留差异并提示，不静默覆盖。原著正文、场景节点、分解资料与游戏运行进度不能混为一种数据。

本设计不涉及 B08、B09，不增加发送硬上限，不改变已存篇章和分段 ID，不批量重置玩家进度。

## 当前边界与根因

`data/storyWeavingPreset.ts` 的 v3 持久态保存分解字段，却没有保存它们是否被玩家改过。hydrate 目前全部刷新内置分解，导致玩家编辑丢失；全部保留则会挡住资源更新。仅凭更新时间或是否不同于当前资源不能区分两者。

写入入口包括剧情面板、开局、加载、回合推进和回滚；`useGameState` 与 Legacy/Teyvat 双向投影也必须保留新的来源元数据，不能只修面板的一条路径。

## 选择与数据职责

采用“内置资源基线＋逐字段覆盖＋独立运行状态”。不使用整系列覆盖，也不凭标题合并系列。

- 基线：按系列 ID、分段 ID、字段名记录资源版本和加载时的确定性字段指纹。指纹仅用于识别版本/变化，不用于身份安全。
- 覆盖：记录玩家修改过的字段及其值。空字符串、空数组是合法编辑，不能用真假判断替代字段存在性。
- 运行状态：当前系列/分段/场景、注入开关、处理及运行状态、进度摘要、历史归档、最近推进判定等沿用现有持久化语义，绝不被资源更新重置。
- 自定义系列：继续完整保存，不套用内置资源更新规则。

新持久态版本为 v4。字段白名单按模型分类显式维护：内置内容字段可覆盖，运行字段独立保存，ID 和来源身份不能通过覆盖任意替换。元数据随游戏存档、设置、快照和导入/导出传递，不另建以玩家姓名为键的全局覆盖表。

## 保存和更新规则

1. 第一次加载资源时，建立对应版本的基线信息。
2. 编辑或 AI 重分解现有剧情资料时，相对该基线求字段差异；记录差异为覆盖。后台自动推进只修改运行字段，不误记为内容编辑。
3. 保存 v4 时写入版本、覆盖和运行状态；未编辑内置正文不重复落盘。玩家真正编辑过的正文必须保存，不能因“它属于内置资源”而删掉。
4. 资源更新时先加载新基线，然后应用已保存覆盖，最后还原运行状态。未覆盖字段采用新资源。
5. 玩家明确选择“恢复此字段的内置值”后删除该字段覆盖；以后该字段随资源更新。界面显示字段来源和资源更新提示。
6. 被删除的分段或系列仍有覆盖或运行引用时保留为“资源已移除的本地保留项”，提示玩家处理，不自动丢弃。新分段只追加，保持现有锚点不变。

## 旧档处理

- v1/v2/v3 或完整旧档没有基线时，只检查原始输入里确实存在的内容字段。与当前资源相同的字段使用资源；有差异的字段保留为“旧档保留，来源未确认”的覆盖，提示一次且可逐字段恢复内置值。
- 归一化补出的默认空字段不能冒充旧档显式编辑。原始输入的字段存在性必须在归一化前保留。
- 来源未知时不宣称一定是玩家编辑；界面说明这是保守保留。重复加载不能重复弹出同一提示或扩大覆盖。
- 同名系列按 ID 隔离；同名玩家的不同存档不能共享覆盖。

## R03：资源双源收口

实测 19 个系列：17 个系列的分段正文一致，但结构字段存在差异；枫丹与纳塔的正文不同。禁止把旧总表覆盖到 public。

建议以游戏实际加载的 `public/data/story-weaving-canon/*.json` 为维护权威源，`data/storyWeavingCanonDecomposed.json` 改为按固定系列顺序生成的兼容产物。收口前逐系列、逐分段输出字段差异和正文差异；确认 public 未遗漏总表独有内容后才能生成。发现独有事实时保留并人工合并，不能以“更长”自动判定更正确。

生成流程显式执行，验证流程只检查不写文件；校验语义内容、顺序、ID 唯一性和现有 canon 校验，而非仅比较原始 JSON 排版。保留枫丹/纳塔扩写与场景节点的回归断言。

## 写入失败与并发

资源加载失败不以过时摘要冒充完整资源；保留当前可用档案并报告失败。保存失败保持编辑草稿可重试，不显示“已保存”。切档后的旧异步保存不允许更新新档。面板编辑与自动推进并发时，沿用 live/delta 合并，覆盖元数据也参与同一边界检查。

## 验收

- 在同一测试中验证：玩家只改概括，新资源同时更新正文和结束条件；读档保留概括并更新另外两项。
- 标题、空字段、列表编辑、正文编辑、AI 重分解、恢复内置值、资源删除、新增分段、自定义系列均往返不丢失。
- v2 缺字段不生成假覆盖；v3 无来源差异保留且提示；再次保存/加载幂等。
- 修改过的剧情通过设置、游戏存档、快照回滚和导入/导出后仍保留来源元数据。
- 两条既有冲突测试改为来源明确的不同输入，保留各自业务断言；不能删除持久化断言换取全绿。
- R03 逐分段差异清单审阅后才收口；生成与验证独立，验证失败不得重写玩家数据。

## 实施边界

先完成资源差异审阅和来源模型，再做保存/装载与各入口迁移，最后改 UI 提示和资源生成门禁。该设计经书面审阅后再形成实施计划；本文件不是完成报告。
