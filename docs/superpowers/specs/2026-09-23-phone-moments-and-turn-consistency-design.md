# 手机朋友圈与回合一致性修复设计

日期：2026-09-23

## 目标与已确认边界

玩家希望每次聊天只看到一条正式正文；手机消息应像角色本人说话，而非复读事件摘要或记忆；正文明确获得、使用、交付的实体物品应与背包一致。手机新增纯文字朋友圈：只有玩家发布动态，玩家能编辑、删除；每条动态最多由三位已认识且达到「生死挚友」的角色评论。

本次不做 NPC 主动发动态、图片动态、点赞、转发、好友可见范围、独立社交数据库或好感度奖励。评论资格是好感度严格大于 100，而非大于等于 100。朋友圈评论不会自行修改好感度或制造 NPC 未亲历的记忆。

## 当前代码证据与待验证假设

- `ChatList` 同时有正式消息列表和独立的流式预览，后者目前只以预览文本非空为显示条件。`aiMessageStage` 构建正式 assistant 消息，变量结算阶段将历史写入活体状态。需用回归用例区分重复来自预览残留、正式历史重复，还是模型正文自身重复；不能仅凭症状选择其中一层修补。
- `composeCourierLetterLocally` 和 `composeCourierReplyLocally` 将 `seed.context`、`recentInteraction`、`unfinishedBusiness` 直接插入模板。回退种子也会把本来给系统看的「已发生事实」描述放进 `context`，因此能够产出「关于安柏对……留下印象」与「对了，……我还记着」这样的元叙述。
- 变量结算对模型输出的 `item` 事实有正式命令通道；正文兜底仅推导扣除事实，且当前扣除识别要求同一句出现「你／旅行者／玩家」。模型漏报获得事实或玩家用其他称谓行动时，背包可能不变。仍需逐层验证事实解析、命令预检、提交和存档是否有额外拒绝原因。
- `CourierSystem` 已作为正式游戏状态的 `手机` 切片归一化和存档；朋友圈应沿用这条边界，不建旁路存储。

## 方案选择

采用现有领域边界内的修复与扩展。相比只在 UI 遮挡重复内容、过滤几个固定短语，这能修复数据源；相比另建社交数据库和完整社区系统，能保持首版范围与现有存档/读档/会话身份保护一致。

## 朋友圈数据与交互

在 `CourierSystem` 新增 `moments` 列表。动态包含稳定 ID、作者 `player`、正文、创建时间与回合、修改时间、修订号、已选评论者 ID 列表、各评论者的生成状态以及评论数组。评论包含稳定 ID、NPC 稳定 ID、显示名、文本与时间。旧存档缺少此字段时归一化为空列表；载入中的 `generating` 状态归一化为可重试的失败状态，避免永久转圈。正文去空白后为 1～500 字；评论为 1～120 字且每条动态最多三条。最多允许 500 条玩家动态，达到上限时提示玩家先删除旧动态，不静默丢弃玩家写下的内容。

手机界面增加朋友圈入口、发布框和时间线。只有玩家动态有编辑、删除入口；编辑保存后修订号递增、旧评论清空并按新正文重新生成，删除后移除动态及评论。删除应提供可撤销操作；取消、空白正文和超长正文不得写入。视图沿用现有手机/冒险者手账视觉与窄屏交互，不影响私聊、群聊的滚动位置。

## 评论生成与一致性

发布或编辑后，从**手机联系人中能唯一关联到已认识 NPC 档案**、且当前好感度 `> 100` 的角色中最多选三位。选择顺序稳定但随动态变化，避免始终同三人。每位角色独立调用手机 API，输入仅含其人设、与玩家共享且可知的记忆、动态正文；不把其他角色的私密信息交叉注入。输出仅允许一条简短评论，不含系统术语、旁白或角色名标签。没有可用 API 时不使用固定模板伪装人设评论。

异步结果写回时同时校验游戏会话 ID、动态 ID、修订号和评论者资格；切档、删帖、改帖、降至门槛以下后到达的旧结果一律丢弃。同一修订号同一 NPC 最多一条评论。单个模型失败不回滚动态或其他评论；界面显示失败并允许手动重试当前修订号中失败的目标，不给已成功评论的角色重复调用。重试时资格仍需重新核验，不能复活旧结果。

## 三项故障的修复策略

### 重复正文

先建立可复现的两类用例：正式消息已写入但预览文本仍非空；恢复/重试后正式历史可能重复。检查原始响应、预览生命周期、消息 ID 和存档历史。按查到的根因修复生成或交接边界，而非把所有同文句子全局去重。验收标准：一条玩家发送对应至多一条正式 assistant 回合；正式回合显示后无第二张流式正文卡；重试、恢复、重 roll 不会误删不同内容的合法回合。

### 手机消息元叙述

把内部投递原因与角色可说的事件事实分开。AI 提示词使用允许角色知道的事件与记忆；本地兜底不得把 `seed.context` 或记忆摘要原句拼成消息，应基于触发类型给简短自然的回复，无法可靠转述时宁可省略事件句。对模型输出做元术语/种子复读校验，拒绝后走安全回退。验收用例使用用户报告的安柏句式，同时覆盖私聊回复、主动来信与不同人物人设。

### 背包结算

从正文、模型事实、正式领域命令、预检结果、活体背包、自动存档逐边界追踪缺失位置。对明确写明玩家实际取得、具名、可携带的实体物品补保守派生；优先沿用模型事实或已有物品目录的分类，无法安全分类时向玩家显示结算警告，不凭空赋予品级。对现有物品的明确使用/交付/遗失扩充第一人称与叙事主语识别，同时排除否定、假设、旁人行动和仅看见物品。已由模型给出的同一物品同一动作不重复派生；同一结算 ID 的重试/恢复不得重复加减。名称模糊或所有权不清的事件保留警告，不凭空创建物品。验收涵盖获得、消耗、交付、数量不足、模型漏报、模型已报告、切档并发及保存重载。

## 测试与交付门槛

每项故障先有会失败的回归用例，再做最小修复；朋友圈先以数据操作、归一化、资格筛选、异步竞态和 UI 交互测试定义行为。完成后运行定向测试、全量单测、TypeScript、ESLint、项目回归脚本及生产构建，并手动检查手机窄屏动态与聊天回合交接。若实测表明重复正文的根因不同于上述两条路径，先更新证据和测试，再改变实现，不用表象遮挡代替根因修复。
