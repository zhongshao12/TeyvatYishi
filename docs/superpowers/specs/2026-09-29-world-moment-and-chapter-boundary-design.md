# 单一世界时刻、记忆来源与篇章同步：边界迁移设计

日期：2026-09-29

## 目标与范围

玩家应能相信同一回合的正文、界面和各系统记录描述的是同一段游戏时间。新产生的记忆与世界树条目必须能够追溯事件发生时的日期、世界、天气、地点及旅行天数；正文明确推进剧情后，侧栏“当前篇章”应对应已经提交的剧情节点。

本规格覆盖本轮需求的前三项：记忆与世界树的时空来源、单一游戏世界时间、当前篇章同步。手机、蒸汽鸟报、任务、NPC、存档和随机事件在本批只迁移到统一时刻的读取/写入边界，不重写各自的业务规则。角色主动联系、朋友圈与群聊、失败结算中心、组件拆分和头像角色分类分别作为后续子项目处理。现有真实时间戳仍可用于日志、保存与请求耗时，但不得冒充游戏世界时间。

## 已确认的选择

- 采用边界迁移，不整体替换现有世界状态。`TeyvatWorld` 的日期、时间、天气、地点和旅行天数仍是当前游戏世界事实的权威来源。
- 每次主回合的时间与剧情结算完成后，生成不可变的“世界时刻”快照。下游消费快照，不各自推算或推进游戏时间。
- 旧存档不能查证的历史字段显示“未记录”，绝不以读取时的当前天气、地点或日期回填旧事件。
- 时间证据与篇章门禁冲突应留下可见结算原因，不静默忽略，也不靠猜测强行改写历史。

## 数据边界

新增独立的 `WorldMoment` 值对象，字段为 `worldName`（目前固定“提瓦特”）、`date`、`clock`、`weather`、`location`、`travelDay`、`turn` 和 `settlementId`。每个字段按类型校验；缺失历史字段用明确的 unknown/空值表示，展示层才翻译成“未记录”。快照一经写入事件，不随当前世界状态变化。

游戏世界状态仍是“现在”的权威。`WorldMoment` 是对某个已提交事件的历史快照，而不是第二个可独立修改的时钟。读档时从已存世界状态构造当前快照；不能从旧记忆反向修改当前时间。手机发送、收到来信或其他非主回合事件只读取当时快照；若某种操作确实要推进时间，必须走同一世界时间结算入口，不能在模块内部改日期。

现有记忆层主要保存字符串，短/中/长期记忆另有同索引归档 ID。因此新写入的即时记忆需要稳定事件 ID 与对应来源快照，字符串层作为兼容投影；不能用文本内容或数组位置充当历史身份。世界树条目扩充来源时刻或来源区间。压缩多个事件时保留最早与最晚来源时刻及来源 ID；展示日期、旅行天数为区间，地点或天气不一致时显示“多地点”或“多天气”，而不是伪装为单一现场。压缩、重试及长期归档均继承来源，不用压缩发生时的当前时刻覆盖事件时刻。`recordedAt` 等技术记录时间继续单独保留。

## 回合数据流

1. 读取同一存档版本的世界状态、剧情进度与回合输入，产生正文和结构化变量事实。
2. 时间结算器在一个地方解析、校验并应用时间变化；剧情对齐器基于正文、玩家输入、地点、场景节点和门禁快照确定下一进度。两者的结果连同结算 ID 一起提交。
3. 提交成功后，从提交后的世界状态生成该回合的 `WorldMoment`。正文、侧栏、记忆、世界树、手机、蒸汽鸟报、任务、NPC、存档和随机事件接收同一快照或通过统一读取接口获得它。异步任务必须携带快照，不在完成时重新读取“现在”。
4. 同一结算 ID 重试或恢复时复用已经提交的时间、进度及快照，不再次推进时钟或重复创建事件。旧版写入路径分批经适配器迁移；全部消费者迁完前保留兼容读接口，但不保留第二套时间计算规则。

## 时间规则

优先级为：正文中明确且可解析的时间证据；其次是有效且不与正文冲突的模型时间事实；最后才是普通行动的默认推进。模型事实必须带证据，并接受与正文、当前世界时刻的交叉校验。跨越午夜的分钟推进、明确“次日/数日后”以及指定目标时刻均由统一结算器换算日期和旅行天数，每次只推进一次。

没有跨日证据时，早于当前时刻的 `set_time` 不可让游戏时钟倒退。明确跨日的正文不能仅因目标钟点小于当前钟点被判作同日回退。无法解析、证据冲突或日期格式无效时，保持原世界时刻、输出具体结算警告；普通行动的保底推进只在确实没有可用时间证据时采用，不用来掩盖冲突。该批先通过现有结算提示呈现警告，后续失败结算中心再统一收纳。

## 篇章规则

“当前篇章”由已提交的剧情编织进度派生，不从正文字符串直接猜测。场景节点完成证据、当前锚点、地点和门禁共同决定是否进入下一分段或系列。正文仅提及其他篇章名称不触发跳转；正文明确完成节点且满足门禁时，应在本回合结算中推进，并让侧栏与存档读取相同结果。

若场景已完成但某个门禁阻止推进，保存明确的阻止原因供结算提示/诊断查看，不继续把旧标签当作无异常状态。异步剧情任务写回之前必须核对存档版本，避免旧任务覆盖较新的进度。旧档加载时只做可验证的进度归一化，不依据最新正文臆造已经历章节。

## 兼容和失败处理

- 旧记忆、旧世界树条目缺失历史时刻时保留原文；历史字段标记未知，不以当前状态补齐。能从现有可靠来源 ID、存档快照或归档元数据验证的字段可迁移，且记录来源。
- 当前世界状态缺失或无法解析时，不写入貌似准确的快照；阻止相关时间提交并保留可恢复的失败原因。不会删除正文或玩家输入。
- 异步压缩失败后重试使用冻结的来源事件与来源时刻；对同一结算 ID 的重复提交是幂等的。
- 手机等模块的技术时间戳与游戏时间戳并存且标签明确。排序与触发游戏内事件只用游戏时刻；耗时诊断仍用真实时间。

## 验收

1. 正文“数小时后”“次日清晨”“数日后”与游戏日期、时钟及旅行天数一致；无证据的倒退被拦截且有提示。
2. 同一回合产生的正文事件、记忆、世界树及已迁移消费者均引用相同结算快照；后台任务延迟完成不会把事件改记到之后的时刻。
3. 压缩前后可追溯来源时间范围；旧档未知历史显示“未记录”；读档不改写当前世界时间。
4. 完成已确认场景后，“当前篇章”、剧情锚点及存档一致；门禁阻止时有可查原因。
5. 重试、恢复、重复结算不会双重推进时间、重复计入旅行天数或重复建档。
6. 单元测试覆盖时间优先级、跨日、多日、冲突、未知历史、压缩来源和幂等；集成回归覆盖主回合→存档→读档→界面及至少一条后台消费者路径。

## 非目标与后续顺序

本批不改变 NPC 主动行为的资格与冷却。后续项目仍遵循已确认规则：只限已有手机联系人，好感度至少 100；只按游戏世界时间推进，在每完成 15 个游戏回合后最多一位角色主动联系玩家，采用全局冷却。之后再处理朋友圈 `@`、群聊 `@全体成员` 失败；再处理失败结算中心、分包循环/大组件拆分及“有头像即原著角色”的分类规则。各批独立验收，不把未实施项写成已修复。
