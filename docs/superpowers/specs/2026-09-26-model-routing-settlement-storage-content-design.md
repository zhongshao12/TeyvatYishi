# 模型投递、结算、存储和内容包增量改造设计

日期：2026-09-26

## 目标与边界

沿用现有 React/Tauri、Teyvat 领域命令、IndexedDB 存档、世界书与酒馆预设机制，补足玩家对“发送了什么、结算了什么、占用了多少、内容是否加载成功”的可见性。四项可独立验收，依次交付。不恢复内置酒馆预设，不切换 UI 框架、不改用通用 JSON Patch、不创建新的存档根。

本轮**不设置发送前硬上限**：不因预估 tokens 阻止请求，也不新增自动裁剪玩家输入、历史、世界书或酒馆预设的逻辑；现有主剧情最近 20 条历史窗口保持不变。上下文诊断只显示预估值、实际 API usage（若提供）、主要占用来源及非阻断提醒。未知模型窗口不猜测为 32K 或 1M；只有玩家显式填写 `maxContext` 时才显示占比。任何提醒都不得被描述为精确 tokenizer 结论。

## 当前基线

- `services/promptModuleScopes.ts` 用 ID 前缀把独立模块分配给变量、手机、蒸汽鸟报等目标；`models/prompts.ts` 的 `scope` 描述场景而非独立模型目标。`ContextViewer` 已有六个上下文页，但主剧情页是当前状态预览，不能冒充上一请求的真实载荷。
- `services/teyvatTurnTransaction.ts` 已预检并原子提交；变量批次保留成功、拒绝和警告。聊天里的 `TurnSettlementReceipt` 已有简略回执，但“背包新增”“同伴更新”等标签不说明具体对象和值。
- 存储页已有浏览器总体占用，存档树已有 `sizeBytes` 估算和逐档导出；该数值是启发式估算，不能当作 IndexedDB 精确磁盘占用，图片共用资源也不应在逐档总计中重复计费。
- 内置世界书已有 `contentVersion` 合并规则；开局、世界书、图鉴等资源的投递和加载失败尚缺统一、可检查的诊断口径。

## 第一批：显式投递目标与上下文诊断

在提示词模块记录中新增独立于 `scope` 的投递目标集合：主剧情、变量、手机、蒸汽鸟报、图鉴、世界树召回、世界树归档、剧情编织。`scope` 仍控制主剧情的开局/常规/元素回响等场景；投递目标决定独立模型能否使用该模块，二者不可互相替代。既有模块按已知 ID 映射一次性归一化，未知 ID 不靠模糊前缀静默投递；设置页明确显示“未指定目标”。用户自建或导入模块可编辑目标，内置锁定模块遵守现有编辑权限。

所有独立模型从同一目标选择器取模块。保留原来的排序与启用条件，先让旧模块在已知映射下行为不变，再迁移调用方。加入“投递诊断”：当前预览列出模块标题、来源、目标、是否启用、是否被选入、未选入原因和预估 tokens；上一真实请求只记录目标、模块 ID、各段长度与总量等元数据，不持久化 API Key 或完整私密提示词。主剧情酒馆预设消息链仍由其专用编译器生成，但必须进入同一诊断统计，区分“预览”和“上次实际发送”。

预估 tokens 仅供观察。如果设置了 `maxContext`，可显示预估占比及非阻断提醒；没有配置窗口则仅显示占用量。即使预估超过配置窗口，仍按用户选择继续发送，最终由提供商决定是否接受；接口返回上下文错误时保留原始玩家消息并显示可操作提示，不伪装成生成成功。

## 第二批：结算回执细化

继续使用持久化变量批次与 `TurnSettlementReceipt`，不增加第二份独立结算历史。对背包数量、NPC 好感度、任务状态、世界日期/时间等支持安全投影的命令，在提交前后从旧/新状态计算具体变化；只展示最终已提交的差异，绝不根据正文推测。拒绝项保留原批次原因，但通过安全映射转成人话；未知或可能含敏感信息的值仍显示“查看变量记录”，不把原始模型文本直接暴露到聊天。重试、恢复、读档按回合及批次 ID 去重；旧批次被压缩时继续显示“记录已压缩”，不补造细节。

## 第三批：存储可解释性与备份提醒

保留现有总体浏览器占用和逐档 `sizeBytes`，把逐档数据明确标为“估算”。另统计已存档正文、增量节点与资源的归属及共享情况：共享图片只列入“共享资源”小计，不重复加到每份存档；无法可靠分摊的空间明示“未归属”，不宣称所有数字之和等于浏览器配额。统计按需触发，不在每次渲染时扫描数据库。已有导出与清理动作保持不变；在长期未导出且存档持续增长时提供可忽略的本地备份提醒，提醒本身不自动导出、不删除任何数据。任何清理仍走原确认流程。

## 第四批：内容资源契约与失败诊断

为内置开局、世界书、图鉴资源提供统一的内容登记表：稳定 ID、类型、内容版本、来源与装载状态。现有 `contentVersion` 仍是世界书内容更新的唯一判据；登记表不复制正文，也不把用户自建世界书当成内置资源。构建期检查 ID 唯一、引用可解析、版本合法；运行时加载失败要指出资源 ID、阶段和恢复入口，不能静默使用空内容或覆盖用户编辑。资源可按现有 Vite/Tauri 分发方式继续交付；只有实测首屏体积或加载耗时有收益时才拆成独立按需包，且离线桌面版必须可用。

## 验收与实施顺序

每批先写失败用例，再做最小实现：①已知/未知模块路由、酒馆预设诊断、未配置窗口不阻断；②同回合重复批次、已提交差异、失败和压缩记录；③共享资源去重、估算标签、提醒可忽略、扫描不阻塞页面；④资源 ID/版本检查与加载失败展示。各批分别运行定向测试、全量单元测试、TypeScript、Lint 与生产构建；桌面及窄屏 UI 另做人工验收。现有未提交的手机回复改动与本设计无关，不纳入提交。
