# 剩余玩家体验问题的分阶段修复设计

日期：2026-09-23

## 目的与范围

玩家希望手机对话、回合结算和存档状态可信且容易理解：连续发消息不会让角色基于旧消息抢答；物品、关系、任务等实际结算可核对；开局前能知道 API 是否配置妥当；长会话与手机页面仍然流畅、清晰。既有世界观、角色设定、存档格式和模型供应商选择保持不变。本设计是对现有工作流的定点修复，不重写整个 `App`、新增战斗/祈愿系统，也不把路线图中未经复现的猜测当成既定故障。

实施分三批，每批可独立测试与交付：①手机回信和结算回执的正确性；②配置、存档、朋友圈状态的可解释性；③移动端可读性与经测量确认的性能瓶颈。后一批不以重做前一批为前提。

## 现状与约束

- 手机发送时，`CourierModal` 依据当前渲染的 `courier` 构造快照并请求回信；`App` 将待处理项按会话 ID 排队，随后把快照交给 `runCourierReplyPass`。快速连续发送可能使请求使用旧消息。必须以已提交的活体手机状态为回信输入，且切档后旧请求不得写入新档。
- 变量结算已有带 `turn`、结果 `ok/kind/reason` 的批次，`VariableDrawer` 可查看，但聊天主视图没有简明的“本回合变化”。回执只能投影正式结算结果，不能从正文猜测已经入账。
- 设置有“测试连接”，开局向导缺少就绪提示；顶部没有与实际持久化动作对应的存档状态。朋友圈已有动态和评论规则，需把资格、失败、编辑清空评论的结果解释给玩家。
- 聊天列表已经按最近 20 回合增量展开。先测量联系人、动态、长会话的真实耗时，再决定局部列表优化；不预设需要整站虚拟列表。
- 工作区有大量尚未提交的既有改动。本设计的实现不得清理、覆盖或顺手提交它们；每批只改相关边界。

## 第一批：手机回信与结算回执

### 手机回信的数据流

`CourierModal` 只发送“会话 ID + 本次玩家消息的稳定 ID + 当前游戏会话 ID”的回信意图，不再把渲染时的 `CourierSystem` 快照当作生成依据。主控层维护每个会话的最后已答玩家消息 ID、待答范围与运行状态。在同一会话最后一次玩家发送后的 500 毫秒内继续发送，重置等待窗；窗结束后，从最新已提交游戏状态读取该会话及可知记忆，合并这一窗内尚未答复的玩家消息，只发起一次模型回信。不同会话各自排队，不串话。

模型运行期间的新玩家消息不混入已经发出的请求，而是进入下一待答范围；当前回信提交后再读取活体状态处理它们。写回前核对游戏会话 ID、会话仍存在、请求覆盖的消息 ID 仍在且未被更早的回复确认。请求失败保留待答范围并显示可重试状态，不用模板假装模型已经回了。切档、解散群聊或删除会话使旧请求失效。被 `@` 点名和群聊全体成员的既有选择规则保持不变；500 毫秒是玩家连续输入的合并窗，不替代既有的角色消息展示间隔。

### “本回合变化”

在正式 assistant 回合下方增加紧凑、可展开的结算回执。其输入是该回合**已提交**的变量命令批次与警告，按原顺序展示：成功变化（例如物品增减、好感度、任务、时间）、失败/拒绝的变化及其可读原因、无变化。正文只描述了动作但缺少可提交事实时，不伪造成功；若现有结算层发出了警告，则显示“未入账”提示并可打开详细变量记录。回执通过回合/批次 ID 关联，重试、恢复和读档后仍与对应正文一致，不展示原始提示词、API 密钥或不必要的调试字段。命令类型繁多时按领域折叠，但失败与拒绝保持醒目。

### 验收

快速同会话连发三条、跨会话交错发送、模型请求期间再次发送、切档/解散/失败重试，均不得出现丢消息、重复回信、旧档写新档或错读旧快照。回执与最终背包、任务、关系和时间一致；同一结算重试不会叠加变化；失败不被渲染为成功。

## 第二批：状态解释与配置引导

开局向导增加就绪卡片，检查主模型 URL、密钥、模型名等本地必要字段，说明变量处理与生图等可选能力；缺失时警告并提供跳转设置入口，但允许继续建档。联网“测试连接”仅由玩家主动点击触发，避免向导打开即耗费额度或泄露密钥。设置页把常用 API 字段及测试入口前置，高级参数保持折叠；不改变已保存的配置结构或导入酒馆预设的优先级。

顶部存档指示由真实持久化生命周期驱动，区分“有未保存更改”“保存中”“已保存”“保存失败”。只有实际写入成功才能显示“已保存”；失败状态持续到后续成功写入或用户明确处理，不能靠定时器消失。手动与自动存档分别标明，切档时旧会话的迟到保存结果不能更新当前指示。失败提示给出重试入口但不阻塞继续游玩。

朋友圈说明只有玩家可发帖、当前有多少位满足评论资格及门槛；没有合格角色或 API 不可用时明确说明不会有评论。编辑动态会清空旧评论并对新修订重新生成，界面在确认编辑前说明这一点。单个评论失败仅重试该角色、该修订，沿用现有会话/修订防旧结果写回的保护。

## 第三批：可读性与性能

先对手机联系人、群聊组建/管理、朋友圈、同伴页和 500 回合聊天做桌面与窄屏基线，记录首次打开、滚动、输入及页面切换耗时。用至少 100 联系人、300 动态、500 回合的测试数据定位瓶颈。只优化经证实耗时的列表或计算：例如设置标签页按需加载、朋友圈分页/增量展示、联系人搜索与关系图的派生数据缓存。已有的聊天 20 回合增量展示不重复改造；缓存按游戏会话和数据版本失效，不能让切档后看到旧联系人。

手机与同伴常用正文以清楚可读为目标：普通文本至少 14px、辅助标签至少 12px，主要触控目标至少 44×44 CSS 像素；窄屏无横向遮挡，滚动容器能到达最后一项，角色名、头像和时间完整显示。上述尺寸是验收目标，不要求所有装饰性图标都扩大。性能优化不得牺牲键盘操作、焦点可见性或屏幕阅读器名称。

## 故障与边界处理

本设计不做破坏性存档迁移。任何模型或网络失败均保留玩家发送内容和已完成结算；未完成请求可重试，不能生成假回信。结算回执以提交结果为准，发现“正文说获得但没有入账”时仍由已有结算/警告流程处理，回执不直接改背包。存档失败不得把内存状态谎称为持久化成功。日志与 UI 不输出 API 密钥。

## 验证与交付顺序

每批先建立能够复现问题的自动测试，再改最小必要边界。第一批重点覆盖并发、消息 ID、会话身份、回执投影与恢复；第二批覆盖本地配置判定、手动测试连接、持久化状态机及朋友圈资格；第三批用可重复的性能样本比较优化前后，并做窄屏/键盘检查。每批运行定向测试、全量单测、TypeScript、Lint、现有回归脚本与生产构建；把实际通过数量、警告和未解决问题如实记录。只在已有玩家体验文档中同步经过验证的行为，不把设计目标写成已经实现。
